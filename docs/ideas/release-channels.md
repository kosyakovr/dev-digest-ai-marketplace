# Idea: stable and latest release channels

- **Status:** draft — research notes, not a spec. Scheme chosen: **C, bare-name dependencies with sha-pinned catalogs**; all open questions decided (see § Decisions). Checks done locally and against GitHub (see § Verified and § Checked against GitHub).
- **Date:** 2026-10-21
- **Goal:** publish new plugins and new versions to a `latest` channel first, and promote them to `stable` once they are proven.

## What the Claude Code docs say

- **There is no channel concept.** One marketplace serves one version of each plugin at a time. Channels are two marketplaces with different `name` values whose entries point at different refs of the same plugin; each user adds the one they want. An admin can assign a channel to a group through `extraKnownMarketplaces`. ([Run release channels](https://code.claude.com/docs/en/plugins/host-marketplace#run-release-channels))
- **`#ref` on the add command** picks a branch or tag of the catalog: `/plugin marketplace add owner/repo#latest`. The command reads only `.claude-plugin/marketplace.json`. ([Marketplace sources](https://code.claude.com/docs/en/plugins/marketplace-reference#marketplace-sources))
- **A marketplace name can be registered once per user**, so the two catalogs need different `name` values.
- **Entries can pin a version.** `github`, `url` and `git-subdir` sources take `ref` (branch or tag) and `sha` (full commit; checked out when set). `git-subdir` checks out one subdirectory, which fits this monorepo. ([Plugin sources](https://code.claude.com/docs/en/plugins/marketplace-reference#plugin-sources))
- **Updates follow `version`.** A user gets a new copy only when the plugin's version changes.
- **Dependencies:** a dependency declared by name alone "depends on whatever version that plugin's marketplace provides". A dependency with a version range resolves against `<plugin>--v<version>` git tags instead. ([Plugin dependencies](https://code.claude.com/docs/en/plugins/dependencies))

## The problem with version ranges

Tags are repository-wide, so a range sees every version ever tagged, whichever channel it was meant for. The first round of checks (below) showed what follows: a dependency ignores the channel catalog and installs at the highest matching tag; latest users get dependencies from stable tags; and an rc installed directly from latest breaks dependents whose ranges do not admit it. Pre-release versions only patch this, at the cost of rc releases cascading through every dependent.

Declaring dependencies by name removes the tags from resolution: each channel's catalog alone decides which version of a dependency users get.

## Scheme C

| | stable | latest |
|---|---|---|
| Marketplace name | `dev-digest-ai` (unchanged, so existing users stay put) | `dev-digest-ai-latest` |
| Catalog lives on | `main`, `.claude-plugin/marketplace.json` | branch `latest`, generated by CI from `main`, never edited by hand |
| Plugin entries | `git-subdir`: `url` = this repository, `path: plugins/<name>`, `ref: main`, `sha: <promoted commit>` | relative paths, so the newest code on `main` |
| Contains | promoted plugins only | every plugin under `plugins/*`, as merged |
| Users add it with | `claude plugin marketplace add kosyakovr/dev-digest-ai-marketplace` | `claude plugin marketplace add kosyakovr/dev-digest-ai-marketplace#latest` |

Rules:

1. **Dependencies by name.** `plugin.json` lists dependencies as bare names (`"engineering-paved-path"`), never with a `version` range, so Claude Code resolves them inside the user's channel.
2. **Plain semver, no pre-releases.** Every change bumps the version, as today. A promoted plugin reaches stable with the same version string it had in latest.
3. **Each catalog is a lockfile, and CI keeps it consistent.** Claude Code no longer disables a plugin whose dependency is incompatible, so the guarantee moves to CI. Each plugin keeps its compatibility ranges in its own metadata, which Claude Code ignores. For each catalog, CI reads `plugin.json` at every pinned commit and checks two things: every dependency is in the same catalog, and its version satisfies the dependent's range. CI runs this for the stable catalog on every PR that changes it, and for the latest set on every merge.
4. **Promotion is one PR per plugin.** It moves that plugin's `sha` in the stable catalog to a commit already on `main`, or adds the entry for a new plugin. A major version of a dependency is promoted in the same PR as the dependents that support it; check 3 refuses anything else.
5. **Tags mark stable releases only.** After a promotion merges, the workflow tags `<plugin>--v<version>` at the pinned commit. Our own resolution no longer reads tags; they serve history and third-party plugins that depend on ours with a range. There is no tag/ref window, because the `sha` exists before the PR is opened.
6. **`main` history is never rewritten**, because every pinned `sha` must stay reachable from `ref: main`.

Users should register one channel only. With both, a plugin from each would install side by side (`x@dev-digest-ai` and `x@dev-digest-ai-latest`).

## What would change in this repository

- **`plugins/*/.claude-plugin/plugin.json`**: dependencies become bare names, with a version bump for `architecture-review` and `sdd-engineering`. Compatibility ranges move to our own metadata.
- **`scripts/check_marketplace.py`**: accept `git-subdir` entries with `sha` in the stable catalog, and add the per-catalog consistency check (rule 3). `check_version_bump.py` stays as it is.
- **`.github/workflows/release.yml`**: generate the `latest` branch on every merge, and tag only on promotion.
- **`scripts/generate_catalog.py` and the catalog site**: read `git-subdir` entries and show each plugin's channel and version.
- **`docs/RELEASES.md` and `CONTRIBUTING.md`**: the channel model, the promotion procedure and the "one channel per user" advice.

## Verified on a throwaway marketplace (2026-10-21, Claude Code 2.1.296)

Setup: a local bare repository served over smart HTTP (`git http-backend` on `127.0.0.1`), because `claude plugin marketplace add` rejects `file://` URLs and the CLI does not register `extraKnownMarketplaces`. Stable catalog on `main` with `git-subdir` entries pointing at the same repository URL; latest catalog on branch `latest` with relative paths. Each case ran in a fresh `CLAUDE_CONFIG_DIR`. The `sha` pin was then repeated against GitHub (see § Checked against GitHub).

**Scheme C (bare-name dependencies, sha pins):**

| Case | Result |
|---|---|
| Stable: install `app` (depends on `"dep"`). Tag `dep--v1.1.0` exists; the catalog pins `dep` at the 1.0.0 commit | `dep` 1.0.0. The tag is ignored, so nothing leaks |
| Latest: install `dep` 1.1.0 directly, then `app` | both install, no conflict |
| Latest: install `app` alone | `dep` 1.1.0, the newest on latest |
| Promotion: move `dep`'s `sha` in the stable catalog to the 1.1.0 commit, no tag | `marketplace update` then `plugin update` moved an installed 1.0.0 (installed as a dependency) to 1.1.0 |

**First round, version ranges (why scheme A was dropped):**

- `git-subdir` to the marketplace's own repository with a tag in `ref` installs, and moving the `ref` updates installed copies.
- Ranges follow node-semver without `includePrerelease`: with tags `1.0.0` and `1.1.0-rc.1`, `^1.0.0` and `^1.0.0-0` both resolve to 1.0.0, and `^1.1.0-rc.1` to the rc.
- A ranged dependency ignores the catalog's `ref`. With tag `dep--v1.1.0` present and the stable entry still at 1.0.0, a dependent with `^1.0.0` installed `dep` 1.1.0.
- Latest users with `^1.0.0` dependents got `dep` from the 1.0.0 tag, not the latest copy.
- With `dep` installed directly from latest at `1.1.0-rc.1`, installing a dependent with `^1.0.0` failed (`Dependency "dep@…" is installed at 1.1.0-rc.1, which does not satisfy: ^1.0.0`), and the dependent shows `failed to load`.

## Decisions (owner, 2026-10-21)

1. Stable keeps the `dev-digest-ai` name; latest is `dev-digest-ai-latest`.
2. Promotion is done per plugin, one PR each.
3. Scheme C: dependencies by name, catalogs pinned by `sha`, plain semver. This replaces the earlier decision to ship `X.Y.Z-rc.N` versions to latest, which scheme C no longer needs.

Rejected: **A**, ranged dependencies with rc versions (tag leaks, rc cascades, a tag/ref window); **B**, a second repository that receives promoted copies (keeps Claude Code's range check, but doubles the repositories and needs sync); exact pins (`=X.Y.Z`), which still resolve through tags and conflict between dependents.

4. No migration path for existing users: there are none yet, so the switch to scheme C does not need to preserve installed copies.
5. Compatibility ranges live in `plugin.json` under `metadata`, e.g. `"metadata": {"compat": {"engineering-paved-path": "^1.0.0"}}` (see § Where compatibility ranges can live).

## Checked against GitHub (2026-10-21)

A local directory catalog whose `git-subdir` entries point at `https://github.com/kosyakovr/dev-digest-ai-marketplace.git` with `ref: main` and a `sha`:

- `research-tools` pinned at `90ae6ec` installed 1.0.0, and `sdd-engineering` pinned at `7f88a8f` installed 0.1.0, although `main` was at 1.0.0. The `sha` pin works against GitHub.
- Moving `sdd-engineering`'s `sha` to `90ae6ec`, then `marketplace update` and `plugin update`, moved it from 0.1.0 to 1.0.0.
- **Caveat for promotions that add dependencies.** 1.0.0 declares three dependencies that 0.1.0 did not have. `plugin update` did not install them, and the plugin showed `failed to load` until they were there; each re-run of `claude plugin install sdd-engineering@…` added one missing dependency. The docs say newly added dependencies arrive through `/reload-plugins` in a session or through marketplace auto-update. The release notes of such a promotion must tell users to run `/reload-plugins`.

## Where compatibility ranges can live

Checked with `claude plugin validate --strict` and by installing each variant from a local catalog (2026-10-21):

| Option | `--strict` | At runtime | Assessment |
|---|---|---|---|
| **`metadata` in `plugin.json`**, e.g. `"metadata": {"compat": {"engineering-paved-path": "^1.0.0"}}` | passes | loads; the bare-name dependency installs from the catalog | **Recommended.** A free-form field Claude Code does not read, next to `dependencies`, versioned with the plugin, so CI reads it at the pinned `sha` |
| A file in the plugin, e.g. `.claude-plugin/compat.json` | passes | loads | Works, but it is a second file to keep in sync with `dependencies` |
| An extra key in the dependency object, `{"name": "x", "compat": "^1.0.0"}` | passes | loads, resolves as a bare name | Not recommended: undocumented, and a future Claude Code field could take that key or change how an object entry resolves |
| `metadata` on the stable catalog entry | not tested | — | Not recommended: it lives in the catalog rather than with the plugin version, and the latest catalog is generated |
| A custom top-level key in `plugin.json`, e.g. `x-compat` | **fails**: `Unknown field 'x-compat'` | — | Rejected |
| One central file in the repository | — | — | Rejected: it is read at `HEAD`, not at each plugin's pinned commit |
