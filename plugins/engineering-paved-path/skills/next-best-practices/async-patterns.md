# Async Request APIs and Await Patterns

Next.js 16 exposes request data only through promises. This file covers how to read `params`, `searchParams`,
`cookies()`, `headers()`, and `draftMode()` correctly, how to type them, and how to avoid request waterfalls.

## What is async in Next.js 16

Synchronous access (allowed temporarily in 15) is fully removed in 16. These must be awaited, or unwrapped with
React `use()` in a Client Component:

| API | Where | Type |
| --- | --- | --- |
| `params` | `page`, `layout`, `route`, `default`, `generateMetadata`, `opengraph-image`, `twitter-image`, `icon`, `apple-icon` | `Promise<{...}>` |
| `searchParams` | `page` (and `generateMetadata` of a page) | `Promise<{ [k: string]: string \| string[] \| undefined }>` |
| `cookies()`, `headers()`, `draftMode()` | `next/headers` | `Promise<...>` |
| `id` in image functions using `generateImageMetadata` | `opengraph-image`, `icon`, etc. | `Promise<string>` |
| `id` in `sitemap` using `generateSitemaps` | `sitemap.ts` | `Promise<string>` |

Exceptions that stay synchronous: `generateImageMetadata` receives plain `params`, and a child
`generateStaticParams` receives the parent's generated values as a plain `params` object.

**Avoid**: `params.id`, `{...params}`, `Object.keys(searchParams)`, `cookies().get('x')`, `for (const c of cookies())`.
All of these treat the promise as a value.

## Type with the generated helpers

`PageProps<'/route'>`, `LayoutProps<'/route'>`, and `RouteContext<'/route'>` are global (no import) once types are
generated by `next dev`, `next build`, or `next typegen`. Pass the route literal to get strict `params` keys and
typed parallel-route slots on layouts.

```tsx
// app/invoices/[invoiceId]/page.tsx
export default async function InvoicePage({ params, searchParams }: PageProps<'/invoices/[invoiceId]'>) {
  const [{ invoiceId }, { tab = 'summary' }] = await Promise.all([params, searchParams])
  const invoice = await getInvoice(invoiceId)
  return <InvoiceView invoice={invoice} tab={String(tab)} />
}
```

```ts
// app/api/invoices/[invoiceId]/route.ts
export async function GET(_req: Request, ctx: RouteContext<'/api/invoices/[invoiceId]'>) {
  const { invoiceId } = await ctx.params
  return Response.json(await getInvoice(invoiceId))
}
```

`searchParams` is a plain object, not `URLSearchParams`; values can be `string[]` when a key repeats, so
normalize before use (recommendation: validate with `engineering-paved-path:zod`).

## Client Components: unwrap with use()

Client Components cannot be `async`. A client page receiving `params`/`searchParams` reads them with `use()`;
for server data, start the promise in a Server Component, pass it down, and unwrap it under `<Suspense>`.

```tsx
// app/recipes/[slug]/reviews.tsx
'use client'
import { use } from 'react'

export function Reviews({ reviewsPromise }: { reviewsPromise: Promise<{ id: string; text: string }[]> }) {
  const reviews = use(reviewsPromise) // suspends until resolved
  return <ul>{reviews.map((r) => <li key={r.id}>{r.text}</li>)}</ul>
}
```

```tsx
// app/recipes/[slug]/page.tsx
import { Suspense } from 'react'
import { Reviews } from './reviews'

export default async function RecipePage({ params }: PageProps<'/recipes/[slug]'>) {
  const { slug } = await params
  const recipe = await getRecipe(slug)       // critical: await it
  const reviewsPromise = getReviews(recipe.id) // secondary: do not await
  return (
    <>
      <h1>{recipe.title}</h1>
      <Suspense fallback={<p>Loading reviews...</p>}>
        <Reviews reviewsPromise={reviewsPromise} />
      </Suspense>
    </>
  )
}
```

## Avoid waterfalls

**Do**
- Start independent requests first, then `await Promise.all([...])`.
- Push slow, independent data into child components behind `<Suspense>` so the rest renders first
  (see [suspense-boundaries.md](suspense-boundaries.md)).
- Defer the `await` until the value is needed. With Cache Components, passing the `params` promise down and
  awaiting it inside a `<Suspense>` keeps the surrounding layout in the static shell.

**Avoid**
- `const a = await x(); const b = await y()` when `y` does not depend on `a`.
- Awaiting `params` at the top of a layout only to forward it; pass the promise instead.

## Request APIs: where they work

- `cookies()` reads anywhere on the server; `.set()` / `.delete()` only in Server Functions or Route Handlers,
  never during Server Component render (headers are already streaming).
- `headers()` is read-only.
- `draftMode()` returns `{ isEnabled, enable(), disable() }`; toggle it in a Route Handler (or Server Action).
- Calling any of these makes the code request-dependent. Previous model: the route renders dynamically.
  Cache Components: the access must sit inside `<Suspense>` (or `use cache: private`), otherwise the route
  cannot be prerendered. Never call them inside `use cache`; read outside and pass values in
  (see [directives.md](directives.md)).

## Metadata and static params

- `generateMetadata({ params, searchParams }, parent)` gets promises; `parent` is a promise of resolved parent
  metadata. `fetch` calls are memoized across `generateMetadata`, `generateStaticParams`, layouts, and pages;
  wrap non-fetch loaders in React `cache()` to share one query between metadata and the page.
- Params listed by `generateStaticParams` are known at build time, so awaiting them does not force request-time
  rendering. With Cache Components, `generateStaticParams` must return at least one entry (an empty array is a
  build error). See [metadata.md](metadata.md) and [functions.md](functions.md).

## Migrating

Run `npx @next/codemod@latest next-async-request-api .` It awaits or wraps with `use()` where it can and leaves
`@next-codemod-error` comments where it cannot; those comments fail dev and build until fixed or changed to
`@next-codemod-ignore`. Then run `npx next typegen` and switch hand-written prop types to `PageProps` and friends.
